2. 為什麼不走既有流程

ffmpeg 直縫出的畫面顯示相機全程橫倒約 90°（地板在畫面上半、天花板在下半）。 既有 run_scene.sh 用固定 yaw、pitch=0 採樣，隱含假設「相機直立」，這個前提不成立。 過去對同類素材的做法是回 Insta360 Studio 走 FlowState 陀螺儀扶正，但那是 GUI 流程。

改法：用 cubemap 六面取代固定 yaw 採樣。六面覆蓋整個球面、不預設任何重力方向， 每一幀的旋轉交給 SfM 自己解 —— FlowState 扶正對 SfM 並非必要，它只是「固定角度採樣」的前提。 整條流程純 CLI 可跑完。

3a. 同幀六面的「假平移」→ 上 rig 約束

第一次重建分裂成 229 + 24 張兩塊。從重建反推每個面相對 f0 的關係：

旋轉全對（誤差 1–2°，證明 cube face 幾何與 ffmpeg v360 慣例正確）， 但六個面是同一支相機、同一個光心切出來的，基線恆為零。實測 0.4–0.7， 而整個場景的相機包絡只有 ±3~6 —— COLMAP 把六面當成六台獨立相機，用編造的平移吸收誤差。

把實測平均旋轉去比對候選矩陣，每個面都明確對應一個理論值（次佳候選差 88° 以上，完全無歧義）： f1=Ry(-90) f2=Ry(180) f3=Ry(90) f4=Rx(-90) f5=Rx(90)。 用這組精確旋轉 + 零平移寫 rig_config.json， matcher 的 97 分鐘完全重用，mapper 只花 10 秒：

5. 下一步：加密角度軸，而不是時間軸

推測真正的瓶頸不在時間取樣，而在cubemap 的角度取樣方式。

  • 六面中 f4/f5（正上、正下）拍到的是天花板與地板 —— 特徵少且高度重複； f5 更正好是持自拍桿的方向，去人程序已砍掉其中 58/63。
  • 真正扛匹配的只有 f0–f3 這個水平環，而它們兩兩相隔 90°、FOV 100°，只有 5° 重疊。
  • 對照家政教室的成功案例：官方縫合後取 6 個 yaw（間隔 60°、FOV 100°），重疊 40° —— 差了 8 倍。

所以下一輪要改成：水平環 8 個 yaw（間隔 45°、FOV 100° → 重疊 55°）＋ 上下各 1 面， 每幀 10 面。相鄰面重疊大增，匹配應該會有質變。

7. 四個 shell 陷阱（都是錯誤被吞掉）

1. set -uo pipefail 少了 -e
   → feature_extractor 選項打錯直接失敗，但 matcher/mapper 照跑，
     兩階段之後才報 "No images with matches"，錯誤鏈跟根因差很遠

2. set -euo pipefail 有了 -e
   → colmap ... | grep -v "^I2026" 把所有行濾光時 grep 回傳 1，
     pipefail 讓整條 pipeline 算失敗，腳本在「匹配已成功」之後靜默退出

3. echo "rc=$?" 裡的 $? 抓到的是同一行 $(date) 的退出碼
   → 命令替換先執行。要先 RC=$? 存起來再 echo

4. 四元數轉換在 180° 爆掉
   → Ry(180) 的 trace = -1，w = sqrt(1+trace)/2 = 0，接著除以 4w 得到
     [0.0, NaN, Infinity, NaN]，寫進 json 也不會報錯。
     改用 Shepperd 方法，並加 round-trip 驗證（實測誤差 ≤ 3.8e-11）

第 1 和第 2 是對立的：-e 沒有時漏掉真失敗，有的時候又被假失敗誤殺。 正解是保留 -e，但在會被濾光的 pipeline 尾端補 || true， 並在每個關鍵階段之後直接查 db 的數量當驗證點，不依賴退出碼。

9. 匹配策略：exhaustive 的替代

139 幀 × 6 面 = 834 張，exhaustive 是 347,361 對（本機約 10 對/秒 ⇒ 9 小時）。 改用 colmap matches_importer --match_type pairs 搭配自訂對清單。

第一次設計失敗了：只取時間窗 ±3 個原始幀間距，把「走回頭」的遠時間匹配整個切掉 —— 而第一輪 exhaustive 的統計明明顯示幀距 8 仍有 7.9% 好對，那正是 loop closure。 結果重建碎成十幾片、BA 的 Hessian 奇異。

影像好對每張影像好對數結果

第二輪 窗±66953,76710.8碎成 14 片

教訓：時間窗式匹配一定要補 loop closure（關鍵幀之間全配對）， 否則重建會變成一條容易斷的鏈。
